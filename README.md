# Waggle

> *The agentic CRM for the people who move the bees.*

**Waggle** is an agentic CRM for a synthetic commercial-beekeeping domain — Meridian Apiaries & Pollination Services.

It surfaces the same data three ways, so every layer of the stack is visible end-to-end:

1. **An inbox + agent flow** — open `/inbox`, click *Extract* on an inbound email, watch the LangGraph order-extraction pipeline draft a structured order with evidence quotes, then *Confirm* to persist it.
2. **A chat copilot at `/copilot`** — a Jinja+HTMX chat UI that routes each turn to one of four tools (RAG-grounded query, order draft, customer-report draft, command), persists every conversation, and lets the salesperson confirm drafts inline.
3. **Two MCP servers** — `mcp_servers/sales_copilot_server.py` and `mcp_servers/customer_reports_server.py` expose the same data over the Model Context Protocol so any MCP client (Claude Desktop, Codex, Cursor, …) can do customer lookup, vector search, fleet-health aggregation, and email drafting.

All three share the same first-class providers (`vector_search`, `inbox`, `erp`, `mailer`, `storage`, `llm`), the same Postgres + pgvector store, and the same fail-loud policy (`.claude/rules/fail-loud.md`).

The name comes from the **waggle dance** — how bees tell each other where the nectar is. In Waggle, it's how agents tell each other where the data is.

Clone the repo, set an `OPENAI_API_KEY` (or `ANTHROPIC_API_KEY`) in `.env`, and run `make build && make up && make migrate && make seed && make demo`. Postgres + pgvector + Redis come up under Docker; no other external dependencies. Dependencies are locked (`pyproject.toml` + `uv.lock`), the image is built from the lock, and CI builds and boots that same image on every pull request.

Suggested walkthrough (about ten minutes):

1. **`/`** — dashboard: 40 customers, 150 seeded orders across the FSM, 40 customer reports. Everything is synthetic; the footer says so on every page.
2. **`/inbox`** — pick an inbound email, click *Extract*, watch the LangGraph agent draft a structured order with the semantic matcher resolving the customer (Stage A hybrid retrieve + Stage B LLM disambiguation), then *Confirm* to persist. A non-order email is refused with an explanation; a provider failure shows an error card with a request id.
3. **`/copilot`** — you land on your own empty conversation with three example prompts that have data behind them: *"What's the varroa trend at Martinez & Sons Orchards?"* (grounded answer with report citations), *"Log a visit for Foothill Orchards — mites at 3.5%, queens healthy, follow up next week."* (report draft), *"Draft an order for Martinez & Sons Orchards — 20 Italian mated queens at $48 each."* (order draft you can confirm). Click a citation chip to open the report it came from.
4. **`/orders`** — click any order: line items, its transition history, and the legal next moves; advance it one step and watch the row badge update.
5. **MCP** — `.mcp.json.example` shows how to wire the two MCP servers into Claude Desktop / Claude Code / Cursor / Codex for the same data via tool calls.

`/health` and `/ready` are public (`/health` carries the deployed commit; `/ready` reports database, pgvector and whether the model key works). Every other route requires the credentials above; cancelling the browser's prompt shows a page that explains the demo and repeats them. Costs: each chat turn is 2–4 model calls, each extraction 5–10; the demo rate-limits model-backed requests per address and per day. Eval quality and known limitations are documented in [`STATUS.md`](STATUS.md) and [`.reports/matcher_phase_i_summary.md`](.reports/matcher_phase_i_summary.md).

## Data

- 40 customers (orchards, honey wholesalers, mead makers, specialty food)
- 150 orders across the 11-state FSM
- 40 apiary inspection reports (plus product data sheets and regulatory docs in the RAG corpus: 133 documents, 276 chunks)
- 80 inbound emails

All of it is generated by `seed/` with a fixed Faker seed and a fixed clock, so two seed runs are byte-identical; names, addresses and domains are fictional (`.test`).

## Quick start

```bash
cp .env.example .env             # then add OPENAI_API_KEY (or ANTHROPIC_API_KEY)
make build                        # build the image from uv.lock (runtime + test stages)
make up                           # boot Postgres (with pgvector) + Redis via Docker
make migrate                      # run alembic migrations against the local DB
make seed                         # populate 40 customers, 150 orders, 40 inspections, embeddings
make demo                         # start the api at http://localhost:5001
```

Local development without the app container (tests, linters, editors) uses
[uv](https://docs.astral.sh/uv/):

```bash
make sync                         # uv sync --frozen → .venv from uv.lock
make lint                         # ruff + pyright
make test-unit                    # every test that needs no database
uv run playwright install chromium   # once, for the browser-driven tests
```

Edit `pyproject.toml` to change a dependency, then `make lock` to refresh
`uv.lock`; the Dockerfile and CI install only from the lock.

Open `http://localhost:5001` and click around:

- **Dashboard** — counts, FSM state breakdown, recent activity.
- **Copilot** — chat with Waggle. Ask a question, draft an order, log a visit report. Each turn is persisted; drafts are confirm-and-save.
- **Inbox** — synthetic inbound mail. Click *Extract* on a row to run the LangGraph agent, then *Confirm* to persist the drafted order.
- **Customers / Orders / Customer reports / ERP log** — the underlying data.

Full reset:
```bash
make reseed     # drop data, regenerate everything
make reset-db   # drop DB entirely and rerun migrate+seed
```

Tear down:
```bash
make down
```

Run tests:
```bash
make test       # full E2E suite in the test image (real pgvector, real sentence-transformers, real LLM when a key is set)
make test-unit  # every test that needs no database, in the local uv environment
```

CI (`.github/workflows/ci.yml`) runs ruff, pyright, the suite against a
pgvector Postgres service, a build of the production image that it then
boots (migrate + seed + `/health` + `/ready`), and `pip-audit` on the lock.

## Architecture

A browser hits FastAPI; an MCP client speaks to the same backend over stdio.
The AI/data-science layer sits between them and the database.

```mermaid
flowchart TB
    U1[Browser]
    U2["MCP client<br/>(Claude Desktop, Inspector, …)"]

    subgraph Web["FastAPI + Jinja/HTMX"]
      direction LR
      Pages[HTML pages]
      API["JSON API · /api/*"]
    end

    subgraph AI["AI / data-science layer"]
      direction TB
      Agent["LangGraph order-extraction agent<br/>classify → semantic-match customer →<br/>structured-output line items →<br/>SKU resolution (semantic matcher)"]
      RAG["Local RAG<br/>sentence-transformers (384-dim) +<br/>pgvector cosine semantic search"]
      MCP["MCP servers<br/>Sales Copilot · Customer Reports<br/>(tools over stdio)"]
    end

    LLM[("OpenAI / Anthropic<br/>(gpt-6.1-terra · claude-sonnet-4-6)")]
    DB[("Postgres + pgvector<br/>17 tables · seeded synthetic data")]

    U1 --> Web
    U2 -->|stdio| MCP
    Web --> Agent
    Web --> RAG
    Agent --> LLM
    Agent --> DB
    RAG --> DB
    MCP --> DB
    MCP --> RAG
    MCP --> LLM
```

Three pieces worth highlighting from a data-science / AI-engineering lens:

- **Structured-output extraction.** The LangGraph agent uses
  `with_structured_output(PydanticModel)` so each node returns validated
  Pydantic objects, not free-text JSON. Customer and SKU resolution both
  flow through the **semantic matcher** (`providers/semantic_matcher.py`):
  Stage A is a hybrid retrieve (pgvector cosine + Postgres FTS, fused via
  RRF, best-entry-per-target); Stage B is an LLM disambiguator
  (model set by `copilot_matcher_disambig_model`) that returns an evidence-grounded `CustomerMatch` /
  `SkuMatch` with confidence. No legacy `rapidfuzz` / Levenshtein —
  removed in Phase I in favor of the semantic path.
- **Local semantic search.** Customer-report narratives are chunked, embedded
  with `sentence-transformers/all-MiniLM-L6-v2` (384-dim), and stored in
  `pgvector`. The Sales Copilot MCP tool runs cosine similarity directly
  in Postgres — no external vector DB.
- **MCP-native surface.** The same data the API exposes via JSON is also
  reachable through MCP tools (customer lookup, customer-report search,
  email drafting), so an LLM client can answer business questions without
  scraping the UI.

## Pages and routes

**HTML pages** (browse `http://localhost:5001`):

| URL | What it is |
|---|---|
| `/` | Dashboard — customer / order / customer-report counts, FSM state breakdown, recent activity |
| `/copilot` | Three-pane chat UI (rail + thread + composer) for the sales copilot. Each turn is persisted; drafts (orders / visit reports) render inline with a *Confirm & save* button |
| `/inbox` | Synthetic inbound mail; click *Extract* to run the LangGraph agent live and see the resulting order draft inline, then *Confirm* to persist it to `orders` |
| `/customers` | Customer directory, market segments, ERP numbers |
| `/orders` | Paginated, filterable by FSM state; click a row for line items, transition history and the legal next moves |
| `/customer-reports/{id}` | Permalink for one report (the target of copilot citation chips) |
| `/customer-reports` | Apiary inspections; click a row to see the full narrative + varroa / disease detail |
| `/erp-log` | Browse the local ERP-sync log (JSON-line events) |

**JSON API** (under `/api`):

| Method + URL | Purpose |
|---|---|
| `GET  /api/customers`, `GET /api/customers/{id}` | List + detail |
| `GET  /api/orders`, `GET /api/orders/{id}` | List (filterable by `state`, `customer_id`) + detail |
| `GET  /api/customer-reports`, `GET /api/customer-reports/{id}` | List + detail |
| `POST /api/agent/extract` | Run LangGraph extraction on an `EmailInput`; returns `OrderDraft` or `ExtractionFailure` |
| `POST /api/search` | Cosine search against `chunks` via pgvector + sentence-transformers |
| `GET  /api/copilot/conversations`, `GET /api/copilot/conversations/{id}` | Sales-copilot conversations (read) |
| `POST /api/copilot/conversations` | Create a conversation programmatically |
| `POST /api/copilot/turns/{turn_id}/confirm-order`, `…/confirm-report` | Persist a copilot-drafted order or visit report |
| `GET  /health`, `GET /ready` | Liveness (with deployed commit) / readiness (database, pgvector, LLM-provider probe, remaining daily budget) — root, not under `/api`, unauthenticated |

OpenAPI docs are at `/docs`; raw schema at `/openapi.json`.

## Flagship demo flow

1. **Inbound email arrives** — the inbox provider surfaces a fixture email ("Hi, can we get 20 Italian queens for our Central Valley site next week?").
2. **LangGraph agent extracts** — customer is resolved via the semantic matcher (Stage A retrieve + Stage B LLM disambig), line items are resolved to SKUs, the order is drafted in state `EXTRACTED`. Visible from `/inbox`.
3. **Order goes through the FSM** — `EXTRACTED → UNDER_REVIEW → APPROVED → SCHEDULED → IN_PROGRESS → FULFILLED → INVOICED`, every step a legal edge of `db/fsm.py` (visible on `/orders`).
4. **ERP sync fires** — the mock writes a JSON line to `/erp-sync-log/`; the order transitions `INVOICED → SYNCED_TO_ERP`. Visible from `/erp-log`.
5. **Sales Copilot answers a question** — "What's the varroa trend at the O'Reilly orchard?" The MCP server queries customer reports, aggregates mite counts, and returns a structured answer with citations.

The full FSM walk (steps 2-5) is also scripted in `scripts/demo.py`:

```bash
docker compose run --rm seed python -m scripts.demo
# or with a specific account / message:
docker compose run --rm seed python -m scripts.demo --account-id sam.oreilly@meridian-apiaries.test
```

This drives one inbound email all the way from extraction through ERP sync,
including a Sales-Copilot-style follow-up email draft. Output is labeled
step-by-step (`[1/5] Preflight` … `[5/5] Copilot`).

## MCP servers

Two servers live under `mcp_servers/`. They are stand-alone Python entry
points, not part of the FastAPI process — they speak the
[Model Context Protocol](https://modelcontextprotocol.io/) over stdio.

| Server | Tools |
|---|---|
| `mcp_servers.sales_copilot_server` | `find_customer`, `list_customer_sites`, `list_recent_orders`, `search_customer_reports`, `draft_followup_email` |
| `mcp_servers.customer_reports_server` | `extract_from_narrative`, `query_by_disease`, `query_by_varroa_threshold`, `aggregate_fleet_health` |

### Run a server directly

```bash
# Sales Copilot — customer/site lookup, customer-report search, email drafting
docker compose run --rm seed python -m mcp_servers.sales_copilot_server

# Customer reports — narrative parsing, fleet-health queries
docker compose run --rm seed python -m mcp_servers.customer_reports_server
```

### Connect an MCP client

A ready-to-edit config lives in [`.mcp.json.example`](.mcp.json.example).
Copy it into your MCP client's config location:

| Client | Config path |
|---|---|
| Claude Desktop | `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) |
| Claude Code (CLI) | project `.mcp.json` |
| Codex | `~/.codex/mcp.json` |
| Cursor | project `.cursor/mcp.json` |

Then fill in:

- `cwd` — absolute path to your local clone of this repo.
- `DATABASE_URL` — point at the host-mapped Postgres
  (`postgresql+psycopg2://agentic_mcp_crm:agentic_mcp_crm@localhost:5433/agentic_mcp_crm`
  when running via `make up`).
- `OPENAI_API_KEY` — for tools that call the LLM
  (`draft_followup_email`, `extract_from_narrative`).

The servers hold a session open on stdio and respond to tool calls. They
share the same `DATABASE_URL` and providers as the FastAPI app, so an
order persisted via `/copilot` or `/inbox` is immediately visible to an
MCP `list_recent_orders` call.

## Security and operations

- **Authentication:** HTTP Basic when `WAGGLE_USER` and `WAGGLE_PASS` are set (`app/auth.py`); the demo publishes its pair on purpose. Credentials are compared as bytes; a cancelled dialog shows an HTML page (`app/templates/401.html`).
- **Headers:** nonce-based Content-Security-Policy (no inline handlers anywhere; HTMX is vendored), HSTS over TLS, `nosniff`, `DENY` framing, Referrer-Policy, Permissions-Policy (`app/middleware.py`).
- **Cross-site requests:** unsafe-method requests the browser marks cross-site are rejected (Fetch Metadata, `Origin` fallback), because Basic credentials are sent ambiently.
- **Spend guards:** per-client-address token bucket and a daily budget on the model-backed routes (`app/ratelimit.py`, `WAGGLE_LLM_RATE_PER_MINUTE`, `WAGGLE_LLM_DAILY_BUDGET`); every model call is attributed and logged with tokens and list-price cost (`providers/llm.py::usage_scope`).
- **Failures:** provider errors are 503s with a fixed phrase, other failures are generic 500s; both carry a request id (`X-Request-ID`) that finds the full traceback in the log. Nothing echoes an exception or a provider message to the client.
- **Visitor scoping:** a signed cookie (`WAGGLE_SECRET_KEY`) keeps each browser's copilot conversations separate under the shared login.
- **Invariants and their guards:** [`docs/INVARIANTS.md`](docs/INVARIANTS.md).

## Guardrails

- **All synthetic data.** Customer names, SKUs, prices, and emails are fictional, generated by `seed/` (reserved `.test` domains only; a test enforces it).
- **LLM provider toggle.** Default is OpenAI (`gpt-6.1-terra` for every user-facing stage, chosen on the extraction benchmark in `docs/benchmarks/2026-11-02-extract-models.md`; `gpt-6-luna` for conversation titles). Every stage's model is a `Settings` field (`app/config.py`) and can be overridden by environment variable. Switch providers with `LLM_PROVIDER=anthropic` + `ANTHROPIC_API_KEY`. The app raises at startup if the selected provider's key is missing.
